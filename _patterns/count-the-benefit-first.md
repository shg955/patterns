## 적용 조건
**코드 생성이 싸질수록 이 패턴의 값이 커진다.** greenfield 에서는 "일단 만든다" 가 합리적일
수 있지만, 성숙한 시스템에서는 신규 경로가 **영구 운영부담**이 된다 — 동결된 계약, 정적
테스트 lock, 램프 운영. 그 부담은 이득과 달리 자동으로 줄지 않는다.

## 안 쓰면 무엇이 조용히 깨지는가
잘 만들어진, 잘 테스트된, **아무도 필요하지 않은 기능**이 영구 운영부담으로 남는다.
그리고 그 기능을 유지하는 비용이 다른 작업의 속도를 깎는다.

## 어떻게 적용하나
1. **이득을 먼저 절대 수치로 낸다.** 연간 달러 · 초 · 건수. 비율(%)로 내지 마라 —
   작은 모집단의 큰 비율이 착수를 정당화해버린다.
2. **계산을 남긴다.** 남기면 검산된다. 우리 사례에서 "월 $2" 가 검산에서 **1.40배 과대**로
   드러났다(실제 $0.87 = 연 $10) — 설계가 의도적으로 남겨두는 구간을 이득에 포함시켰기 때문이다.
3. **그 수를 비용과 같은 단위로 놓는다.** 개발 시간 · 라이브 코드 회귀 면적 · 재기동 횟수.
4. **작으면 기각한다.** 기각도 산출물이다 — 다음 사람이 같은 것을 다시 제안하지 않는다.

```
soxl#76   유휴현금 파킹 자동화
초기 추정  월 $2
검산      slack=25 가 밴드 내부 $263.67 를 의도적으로 안 파킹한다
                → 실제 대상 $664.95 → 월 $0.87 → 연 $10
비용      라이브 회계 경로 변경 + 재기동
판정      기각. 사용자도 기각했다
```

## 적용됐는지 확인하는 방법
**"이 작업을 안 하면 1년에 얼마를 잃나" 에 숫자로 답해라.** 답이 안 나오면 아직 세지
않은 것이고, 답이 개발 비용보다 작으면 기각이 맞다. 이득을 못 세겠으면 그 사실 자체가
결론이다 — "세지 못했다" 와 "크다" 는 다르다.

## 잘못 적용하면
이득을 세는 것이 "하지 말자" 의 근거로만 쓰이면 개선이 멈춘다.
**자본·규모에 선형인 이득**은 "지금은 작지만 나중에 커진다" 로 **보류**하는 것이 맞다 —
기각과 보류는 다르고, 보류는 설계 산출물을 보존한다.
