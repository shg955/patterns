## 적용 조건
지금까지 **조건 없이 성립한 유일한 패턴**이다. 테스트가 없는 코드베이스에서도 성립하는데,
그때 harness 는 "테스트" 가 아니라 **실측 스냅샷 비교** 형태를 띤다 — 작업 전후로 상태를
떠서 diff 하는 것으로 시작하면 된다.

## 안 쓰면 무엇이 조용히 깨지는가
에이전트가 자기 산출물을 자기 기준으로 통과시킨다. 실패가 성공으로 기록되므로 대시보드·로그·
테스트 결과가 전부 green 인데 실제로는 안 돌고 있다. **깨진 것이 시끄럽게 알려주지 않는다**는
게 이 실패의 성질이다.

## 어떻게 적용하나
1. **소스 오브 트루스를 지목한다.** 에이전트가 만들지 않았고 바꿀 수 없는 것 — 프로덕션 DB,
   서버 자체 계측, 상류 API 응답, 이전 커밋의 스냅샷.
2. **기준을 에이전트가 만든 산출물에 두지 마라.** "테스트가 통과했다" 는 에이전트가 테스트를
   썼다면 증거가 아니다. "행수가 변하지 않았다" 는 스냅샷을 에이전트가 떴다면 증거가 아니다.
3. **검증자를 분리한다.** 만든 에이전트와 검증하는 에이전트를 다르게 하고, 검증자에게
   **원본 요구사항**을 주되 구현 서술은 주지 마라(구현을 보면 그 프레임을 따라간다).
4. **게이트를 도구가 아니라 사실로 정의한다.** `git diff` 가 비어야 한다 같은 게이트는
   작업트리 상태에 의존해 **기준선에서 이미 실패**할 수 있다. 우리 티켓 4건의 착수 게이트가
   전부 그래서 무효였다 — 미커밋 변경 2,015줄이 이미 있었다. 대체: **md5 매니페스트를 떠서
   그 스냅샷 대비 diff**.

```
나쁜 게이트   git diff --stat bot/main.py 가 빈 출력    ← 기준선에서 이미 실패
좋은 게이트   착수 시 md5 매니페스트 → 종료 시 재계산 → 소유 파일만 변경
나쁜 증거     "테스트 19개 통과"(에이전트가 쓴 테스트)
좋은 증거     "전 테이블 행수 diff 0"(DB 가 소스 오브 트루스)
```

## 적용됐는지 확인하는 방법
**게이트를 기준선에서 먼저 돌려라.** 아무 변경도 하지 않은 상태에서 게이트가 통과하지
않으면 그 게이트는 무엇도 판정하지 못한다. 우리는 이걸 안 해서 4개 티켓의 게이트를
전부 무효 상태로 배포 직전까지 들고 갔다.

## 잘못 적용하면
harness 를 에이전트에게 "고쳐도 되는 파일" 로 주면 즉시 무력화된다. 숫자가 안 맞을 때
코드를 고치는 대신 기준을 고치게 된다. 실제로 DoD 숫자가 틀렸을 때 개발자가 코드를 맞추도록
"숫자를 고치지 마라, 틀렸다고 판단되면 물어라" 를 명시해야 했다.
